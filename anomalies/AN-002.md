# AN-002: Run sampler recorded cumulative counters as per-rep values
Found: 2026-09-24, Hermes · Severity: weakens results

## What happened
The D-matrix sampler (clock/sweep_master.sh) wrote the sink's
cumulative stalls / stall_s / tokens totals into per-rep rows as if
they were per-rep measurements, and sampled by "last log line". When
the sink's log froze mid-cell (100k aligned, reps 2-3), consecutive
reps recorded identical rows including the 1s-window rate field. The
rate field itself is a 1-second window and inflates during backlog
catch-up (a recorded 4.29M tok/s against 4.0M offered).

## How it was detected
Rep 2 and rep 3 of the aligned 100k cell matched exactly in every
column including rate — two 75s windows cannot produce identical
1s-window rates and identical cumulative stall counts.

## What it touches
- Results: the first D pass (aligned.csv, random.csv,
  per-engine.csv, 2026-09-24) → action: annotate (interim only; the
  tokens-diff rerun supersedes its rate numbers)
- No findings or claims rest on these rows.

## Fix and guard
The sampler now records the cumulative `tokens` column so delivery
is a diff over each 75s rep boundary, and d_analyze.py excludes any
rep whose token counter did not advance (marked frozen). Guard: a
row is only accepted when tokens increased since the previous rep.
