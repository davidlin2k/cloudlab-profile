### Instrument record (every error preserved)

The memo's exact bpftrace command cannot run on this host: bpftrace
0.20.2 fails to resolve `struct mlx5_core_cq` (the type is in the
mlx5_core module BTF -- `bpftool btf dump` shows STRUCT 'mlx5_core_cq'
size=192, 'cqn' type_id=35 bits_offset=0 -- but 0.20.2 resolves
vmlinux BTF only) and then fails to resolve every scalar cast tried
(u32, uint32_t, int, long, s32, u64 -- all "Cannot resolve unknown
type"). The recorded fallback keys counts on the CQ object pointer
(no cast): `kprobe:mlx5e_completion_event { @cq[arg0] = count(); }
interval:s:1 { time(); print(); clear(); }`. Object addresses are
stable across cells. The CQ -> RQ/ICOSQ mapping is unavailable (the
devlink rx dump is refused), so object roles are undetermined.
t2-1 and t2-2 carry the instrument-failure records; t2-3/4/5 carry
pointer-keyed counts.

### What the instruments can and cannot settle (recorded, not
interpreted)

The devlink rx dump being refused means the posted-buffer counts and
the CQ consumer/producer indices -- the two fields that distinguish
"completions pending with no event" (A) from "no posted buffers" (B) --
are not observable on this platform. The counters show the queue's

the wire), and queue 7's CQ accounting (ch7_events) silent through the
stall while other CQ objects keep receiving events; but the A/B
decision is deferred to the sources (task 4's ring-size A/B and the
driver sources) rather than claimed here. No interpretation accompanies
this addendum.
