## Question

T1a called the threaded-NAPI stall DEVICE/FIRMWARE on the r6615
(AMD EPYC + mlx5).  If the same stall reproduced on a different
driver and CPU family (i40e on Intel Xeon), that call would be
wrong and the bug report could not go out as drafted.  T1b runs
the r6615 cell protocol on 4x Clemson c6420 (2x16c Xeon Gold
6142, X710-DA2) with arms defined by their relation to the IRQ
core (the T1e lesson), n=8 each, two DUT/sender pairs, four
randomized blocks per pair.

## The confound (the memo's wording, kept)

This sweep changed BOTH the NIC driver (mlx5 -> i40e, including
the interrupt re-arm mechanism: i40e re-enables via a register
write, not mlx5's CQ arm/EQ) AND the CPU platform (EPYC -> Xeon).
A clean result here is consistent with T1a's device-side call;
it cannot, by itself, isolate WHICH of the two differences
matters.  The pre-verified breaker for this confound is Utah
xl170 (Broadwell + ConnectX-4 Lx, i.e. Intel + mlx5 --
notes/confound-breaker-xl170.md).  Per DR-015 the breaker runs
"only if every arm is clean" -- which is now the case -- so the
PI decides whether to spend nodes on it.  It was NOT run
unbidden.

## Day-4 accounting measurement (C-014 / AN-007 on the c6420 pair)

tx0=clnode195 as receiver, clnode186 as sender, 158k pps 64 B,
60 s, IRQ core cpu6, perf cycles+ref-cycles over the aligned
window; busy_s = ref-cycles / TSC (2.6 GHz); /proc/stat busy =
user+nice+system+irq+softirq+steal in USER_HZ (/100).

| kernel | stat busy (60 s) | PMU busy (64 s) | ratio |
|---|---|---|---|
| 6.8.0-138 stock (Ubuntu 24.04 image default) | 0.45 s | 47.31 s | **105x** |
| 6.17.8-061708 (the T1B/r6615 kernel) | 7.95 s | 11.40 s | 1.4x |

Kernel facts (stock 6.8.0-138): CONFIG_IRQ_TIME_ACCOUNTING **not
set** (HAVE=y), CONFIG_NO_HZ_FULL=y, HZ=1000, /proc/cmdline has
**no nohz_full=** argument.

Per the memo's branching: **an undercount appears with
IRQ_TIME_ACCOUNTING unset and no nohz_full= on the command line
-> the criterion is IRQ_TIME_ACCOUNTING-unset alone, and C-024
widens.**  The same hardware/protocol on 6.17.8 (1.4x) is the
instrument control: the gap follows the kernel config, not the
platform.  First stock run recorded PMU 38.28 s vs stat 0.36 s;
the stock kernel's stat busy varies run to run (sub-tick burst
sampling at 100 Hz), the PMU number is stable (38.3-47.3 s).

CLAIMS.md C-024 is updated in this pass: the second-platform
measurement is added as evidence and the claim now covers
"IRQ_TIME_ACCOUNTING unset (regardless of nohz_full)".

## Accounting notes (honesty items)

- The ~2.7% sent-vs-received gap in the flood lines is in the
  SENDER's k5blast count and is identical across all 32 cells and
  the IRQACCT runs; receiver-side accounting (ethtool rx-7 ==
  the kcore probe's per-queue packets) is exactly conserved and
  port.rx_discards stayed 0.  It is a send-side artifact, not
  receiver loss.
- The IRQACCT 6.8 leg initially read PMU==0.38 s because
  ref-cycles stop in idle (the ratio cycles/ref is meaningless on
  an idle core); the AN-007 derivation (ref-cycles / TSC) is the
  fix.  irqacct_run.sh records perf.csv, stat samples, per_cpu_count,
  pkts0/1 + discards and the TSC line for every run.
- probe offsets: vsi->rx_rings is +3304 on 6.17.8 (the 6.18.9
  derivation +3312 lands on tx_rings -- verified against ethtool's
  per-queue counters before any cell ran; recorded in
  notes/platform-c6420.md and the day-1 checkpoint).
