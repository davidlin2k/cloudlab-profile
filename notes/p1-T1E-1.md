# p1-T1E-1: T1e -- does placing the poller in its IRQ's L3 cluster fix the stall?
# (DR-013 addendum T1e; verdict: NO -- 5/8 wedged with the mechanism
# verified; the patch is DROPPED per the pre-registered decision rule)

Question (the memo): prototype a small patch that gives a threaded
NAPI poller a default cpumask of the L3 siblings of its IRQ's
effective affinity, re-applied on reset; re-run the UNPINNED arm
(8/8 stalled before), n=8; 0-1/8 = send the patch with the report as
an RFC, >=3/8 = placement alone doesn't fix it, drop the patch and
keep the data. The pre-registered prediction (specs/p1-T1E.md, only
prior = pin10's 0/8): the correctly-placed poller should NOT wedge.

## Attempts (honest trail)

1. **Creation-hook patch** (v2): set the mask in napi_kthread_create
   from the IRQ's effective affinity. Built and ran (7/8 wedged) --
   then INVALID as a mechanism test: mlx5e assigns the IRQ AFTER
   thread creation (n->irq unset at the hook; the pollers floated
   across clusters), so the patch never bound. Data kept for the
   record, superseded.
2. **set_irq-hook patch** (v3, netif_napi_set_irq_locked): built,
   booted (build #6), ran (T1E-RUN2) -- STILL didn't bind: at the
   call site the effective affinity is the boot-time spread, so the
   single-cpu guard skips, and nothing re-fires when the per-cell
   preflight narrows the affinity later.
3. **Notifier patch** (v4, the shipped prototype): mlx5e opts into
   the core napi_config machinery (netif_set_affinity_auto, the same
   opt-in bnxt/ice/idpf use), and netif_napi_irq_notify additionally
   re-applies the thread mask from the new effective affinity when it
   narrows to one cpu. Build #7 (05:31:34Z), booted, T1E-RUN3.

## Binding verification (attempt 3)

- T1E-1's poller cpu histogram (282,654 samples): cpu 40 dominant
  (279,810) -- cpu 40 is inside cluster(8) = {8-11,40-43}, i.e. the
  L3 siblings of the IRQ's cpu 8. The pre-patch runs floated on
  45/13. The mechanism bound in every run-3 cell.
- The live thread mask reads 0-63 between cells: the mask applies on
  the affinity change (per the design) and the post-cell recreated
  thread rebinds on the next change.

## Result (run 3, n=8, all cells valid after refills)

**5/8 WEDGED** (T1E-1,2,4,6,8 yes; 3,5,7 no). >=3/8.

## Decision (per the frozen rule)

**Drop the patch. Keep the data.** Placement of the poller inside its
IRQ's L3 cluster does not prevent the stall. No RFC patch goes out;
the report and the June-RFC reply keep the negative result.

## Reading (facts only)

- The result independently confirms T1a: during a wedge the device
  stops raising completions/EQEs entirely (branch 3), so no poller
  placement can serve completions that are never raised. The two
  experiments agree without being built on each other.
- Consistent with the earlier matrix: the wedge is not a function of
  where the poller runs (T1A's device-state capture + this run).
- The notifier mechanism itself works and is small (5.5 KB patch,
  drivers-side opt-in + a core re-apply hook); it is recorded here
  and in p1/t1e-napi-thread-cpumask.patch (the repo copy = v4) for
  the report's appendix, but is NOT proposed upstream (the memo's
  rule: >=3/8 = drop).
