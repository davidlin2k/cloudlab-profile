# DR-002: Paper 1 reframe -- "receive-overload protection on modern
# Linux is broken three ways" (PI-proposed, conditional)

Date: 2026-09-24 · Status: PROPOSED (conditional on the AN-003 root
cause being confirmed by the wdiag A/B) · Trigger: PI review of
DR-001/AN-003 and the fig1-3 dataset

## The proposed paper
Receive-overload protection on modern Linux is broken three ways:
(1) the default has none since the 6.5 revert (P0 collapses to 0.2%
of offered at 2x knee); (2) the recommended fix, threaded NAPI, wedges
on a widely deployed NIC because of a driver heuristic that assumes
softirq-side NAPI (AN-003 + the mlx5 poll-affinity hypothesis); (3) the
configuration that works -- separating the application from its
interrupt core while processing stays inline (P0X: 97.5%/74.2% at
1.5x/2x knee) -- is exactly what RFS and aRFS undo by design. The
paper then carries a root cause, a fix (skip the affinity check when
NAPI is threaded), and an evaluation (stock vs patched driver).

## Literature state (2026-09-24 searches)
- KNOWN and DIFFERENT: Sochnev, "[PATCH net v2] net: yield the CPU on
  every exit of the threaded NAPI poll loop" (v1 2026-08-14, v2
  2026-09-02; Fixes: 29863d41bb6e "net: implement threaded-able napi
  poll loop support"). Symptom: the kthread NEVER YIELDS (spins) under
  load on PREEMPT_NONE; unmerged in Linus's tree as of v2. Ours SLEEPS
  with the queue dead -- not this bug.
- No mlx5 poll-affinity vs threaded-NAPI fix found (first pass).
- The idiom has a CANONICAL CLEANUP SERIES, which sharpens the novelty
  claim: Damato, "[RFC net-next 0/6] Cleanup IRQ affinity checks in
  several drivers" (2024-08-12, patchew 20240812145633.52911-1): "a
  check in their napi poll functions to determine if the CPU affinity
  of the IRQ has changed. If it has, the napi poll function returns a
  value less than the budget to force polling mode to be disabled, so
  that it can be rescheduled on the correct CPU" -- repeated in at
  least 5 drivers (i40e, iavf, mlx4, mlx5, gve). The series' outcome
  moved affinity-mask tracking into the core (netif_napi_set_irq). So
  the patch story is: a known softirq-era idiom, a known core-helper
  cleanup, and the MISSING THREADED-NAPI EXEMPTION -- our contribution.
- mlx4's exact code (en_rx.c, from the 2014 trusty SRU thread that
  created the per-poll check): cpumask_test_cpu(smp_processor_id(),
  cq->aff_mask) -- "Current cpu is not according to smp_irq_affinity -
  probably affinity changed. need to stop this NAPI poll, and restart
  it on the right CPU" -- reads the REQUESTED mask
  (irq_desc_get_irq_data(...)->affinity).
- 2019 AF_XDP thread (openwall netdev): "i40e and mlx5e try to stop
  NAPI polling by returning a value less than budget if CPU affinity
  changes... when this situation happens, it kills the performance" --
  the pre-wedge underperformance mechanism (arm/poll 0.75) is this same
  idiom, already performance-visible in 2019.
- gve avoids rescheduling NAPI off the IRQ's CPU and arms the IRQ
  instead (per PI review).

## Second driver and the patch framing
Frame the fix as a core-level exemption (skip the affinity check when
NAPI is threaded, ideally via netif_napi_set_irq's core path) + a docs
fix to networking/napi.html's "pin each kernel thread ... the same CPU
as the CPU which services the interrupt" sentence. Second-driver test:
Intel i40e on CloudLab r650 nodes -- the SAME external dependency as
Fig. 10's platform question; one reservation decision unblocks both.
- The kernel NAPI documentation itself encodes the broken assumption:
  "It is recommended to pin each kernel thread to a single CPU, the
  same CPU as the CPU which services the interrupt" (docs/networking/
  napi.html). The P3/P4 rungs deliberately break that recommendation --
  which is exactly where mlx5's 2017-era poll heuristic misfires under
  the hypothesis.

## PRE-REGISTRATION OPERATIONALIZATION (recorded 2026-09-24 14:2xZ,
## before the matrix restarted; the predictions above are untouched)
- "ch7_aff_change delta" rates are graded on the ACTIVE window (the
  first min(onset, 30 s) of the cell): a wedged queue polls nothing,
  so any whole-cell average dilutes the rate by the dead tail. Both
  the active and whole-cell rates are reported per cell.
- Onset: reference = the cell's peak per-window consumption; below 5%
  of offered from the first window = onset at win[0] (instant wedge);
  otherwise the first permanently-dead window (AN-003 definition).
- Cell validity gate = the WIRE (rx_packets_phy delta): wire full but
  driver processing flat is the wedge itself (valid data, class
  WEDGE-CLASS); wire flat = sender failure (cell invalid). A gate on
  ch7_poll would have invalidated the most severe cells.
- Independent variable verified where it acts: the queue-7 poller is
  napi/enp195s0np0-8263 (identified by flood-stime growth; mapping
  8256+q), pinned by exact /proc/comm name each cell with the pid
  recorded in pin-target.txt. (p1pol.sh's schedstat-max cache in
  /root/p1/napi-pid-q7 selects the same thread -- past rows keep their
  arm labels.) Both requested and effective IRQ affinity lists are
  snapshotted per cell.
