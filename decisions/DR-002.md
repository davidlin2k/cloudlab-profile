# DR-002: Paper 1 reframe -- "receive-overload protection on modern
# Linux is broken three ways" (PI-proposed, conditional)

Date: 2026-09-24 · Status: PROPOSED (conditional on the AN-003 root
cause being confirmed by the wdiag A/B) · Trigger: PI review of
DR-001/AN-003 and the fig1-3 dataset

## The proposed paper
Receive-overload protection on modern Linux is broken three ways:
(1) the default has none since the 6.5 revert (P0 collapses to 0.2%
of offered at 2x knee); (2) the recommended fix, threaded NAPI, wedges
on a widely deployed NIC because of a driver heuristic that assumes
softirq-side NAPI (AN-003 + the mlx5 poll-affinity hypothesis); (3) the
configuration that works -- separating the application from its
interrupt core while processing stays inline (P0X: 97.5%/74.2% at
1.5x/2x knee) -- is exactly what RFS and aRFS undo by design. The
paper then carries a root cause, a fix (skip the affinity check when
NAPI is threaded), and an evaluation (stock vs patched driver).

## Literature state (2026-09-24 searches)
- KNOWN and DIFFERENT: Sochnev, "[PATCH net v2] net: yield the CPU on
  every exit of the threaded NAPI poll loop" (v1 2026-08-14, v2
  2026-09-02; Fixes: 29863d41bb6e "net: implement threaded-able napi
  poll loop support"). Symptom: the kthread NEVER YIELDS (spins) under
  load on PREEMPT_NONE; unmerged in Linus's tree as of v2. Ours SLEEPS
  with the queue dead -- not this bug.
- No mlx5 poll-affinity vs threaded-NAPI fix found (first pass).
- The kernel NAPI documentation itself encodes the broken assumption:
  "It is recommended to pin each kernel thread to a single CPU, the
  same CPU as the CPU which services the interrupt" (docs/networking/
  napi.html). The P3/P4 rungs deliberately break that recommendation --
  which is exactly where mlx5's 2017-era poll heuristic misfires under
  the hypothesis.
