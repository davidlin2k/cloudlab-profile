# DR-013 (operative): Close-out of the receive-path investigation, Sep 28 – Oct 16

**Decision.** The investigation closes. Two final experiments answer the two questions that decide what the stall *is*. After that we ship three things: the workshop paper, a bug report, and a reproducible archive. No new hypotheses after the two experiments. Anything unexpected goes into an anomaly file, facts only, and waits for me.

## 1. Final experiments (pre-register each before running; freeze the rule in `specs/`)

**T1a. Who owns the silence? Device-state capture during event-silent gaps.** Due Wed Sep 30; hard stop at 3 working days.
- **Setup:** pin46 arm on clnode366, same config as `p1-LOCALITY`.
- **Tools:** extend the existing `rq1_probe.py`, `eqdump.py` and `arm_sn_logger.sh`. Don't build anything new.
- **At 1 kHz, log across each gap:**
  - the CQ: unconsumed completions at the consumer index (already done);
  - the EQ: the entry at the EQ's consumer index (owner bit), and every EQ re-arm (consumer index plus arm flag);
  - the IRQ: per-CPU interrupt count for the queue's vector, and its affinity at gap onset;
  - counters: `rx_packets_phy`, `rx_out_of_buffer`.
- **If the EQ re-arm site is inlined and can't be probed,** record that in the spec and read the EQ doorbell record instead.
- **Capture ≥ 5 event-silent gaps.** Decision rule, frozen:

| During the gap | Owner | Consequence |
|---|---|---|
| EQ holds new, unconsumed entries, but the vector's interrupt count doesn't move | Interrupt delivery (host or platform) | Report with the IRQ trace; check affinity changes at onset |
| EQ was not re-armed after its last event | Host driver (mlx5 EQ handling) | netdev report with a mechanism; the one branch that could reopen the paper question, which is my call, not yours |
| EQ empty and armed, CQ armed, completions pending | Device/firmware | Vendor bug report |

  Buffer exhaustion (`rx_out_of_buffer` climbing) is expected as a *consequence* of no polling. Don't classify on it.
- **If** the EQ state can't be read reliably by the deadline, mark T1a "open" and stop.

**T1b. Does another NIC show the cross-L3 effect?** Due Fri Oct 2; hard stop at 4 working days, including reservation.
- **Hardware:** reserve Clemson c6420 (i40e) **today**. If unavailable, use the Utah c6620 (ice); the alternatives are listed in `notes/p2-CLNODES.md`.
- **Topology first:** write the equivalent of `notes/topology-n1.md` for that host before choosing CPUs.
- **Arms:** threaded NAPI on one flooded queue. Poller pinned on the same L3 as the IRQ core vs a different L3, same NUMA node. n = 8 each, same flood and duration as `p1-LOCALITY`.
- **Detector:**
  - Port the readiness probe to i40e (the descriptor-done bit in place of the CQE ownership bit) only if it takes ≤ 2 days.
  - Otherwise use the coarse detector: queue `rx_packets` frozen while drop counters climb.
  - Record which detector each cell used.
- **Decision:** ≥ 3/8 stalls on cross-L3 with ≤ 1/8 same-L3 means the effect generalizes. 0/8 on both means it's ConnectX-specific. Anything between is "inconclusive", and we report it as that.

**T1c. Strengthen the workaround claim.** Fold into week 1.
- Run 12 more same-L3 (pin10) cells on clnode366. 0/8 only bounds the stall rate below 37%; 0/20 bounds it below about 14%. The bug report's workaround sentence needs the latter.
- Read the ConnectX-6 firmware release notes after 20.43.3608 for any EQ, CQ or event fix, and record the result. **Do not flash firmware** on CloudLab nodes without CloudLab's written OK.
