1. Fix the utilization metric (S2, Friday, September 25)
Why: in P0X at 390k packets/s, cpu8_busy_s reads 0.16–0.31 s over a 60 s run, although core 8 processes every packet. Figure 3 and every cost estimate depend on this metric.
Steps:
Compute per-CPU busy time from every /proc/stat field: user + nice + system + irq + softirq + steal. Store each field separately in the counters JSONL, not just the total. This stays correct whichever way the kernel accounts IRQ time.
Cross-check one P0X cell at 390k with perf stat -a -C 8 -e cycles -- sleep 60.
Recompute Figure 3 and the per-packet costs. Rerun the knee model with the corrected costs.
Done when: core 8's busy share in P0X at 390k reflects its receive work, and the recomputed model's miss is recorded, whatever it is.
Record: FINDINGS entry, updated Figure 3, and C-014 moved to Supported or Refuted. Add "softirq execution context" to the confound list in the lab handbook.
2. Control-plane stall test (S1, Friday, September 25; about one hour)
Why: in P0 under flood, ordinary threads on the interrupt core get about 0.2% of it. Per-CPU kernel workers are ordinary threads.
Pre-register first, in the spec: at 2× the knee in P0, each operation below takes over 1 s. Falsified if all stay under 2× their idle baseline.
Steps: run each operation 5 times idle, then 5 times during a P0 flood at 2× the knee, and 5 times during a P0X flood as contrast:
/usr/bin/time -f %e timeout 120 sh -c 'ip link add dummy0 type dummy && ip link del dummy0'
/usr/bin/time -f %e timeout 120 sh -c 'ip netns add t1 && ip netns del t1'
/usr/bin/time -f %e timeout 120 sh -c 'echo 1 > /proc/sys/vm/drop_caches'

Run everything over the control network. If anything hits the 120 s timeout, stop the flood and record it.
Record: a result note, and a new claim if the prediction holds.
3. Wedge tracing (S1, Monday, September 28; one day, strict)
Why: the affinity hypothesis is refuted, so we trace. No new theory is allowed until a timeline exists.
Arms: unpin (fastest onset) and ali-P4. Three cells each. Keep the flood on until a wedge is detected, plus 10 s. Then stop the flood, keep tracing 20 s, then run the 10k packets/s probe.
Trace, all on one clock:
trace-cmd record -C mono -b 262144 -o wedge-$ARM-$REP.dat \
  -e napi:napi_poll \
  -e irq:irq_handler_entry -f 'irq == 312' \
  -e irq:softirq_entry -f 'vec == 3' -e irq:softirq_exit -f 'vec == 3' \
  -e sched:sched_wakeup -e sched:sched_switch -e sched:sched_migrate_task \
  -p function -l mlx5e_napi_poll -l mlx5e_completion_event \
  -l napi_complete_done -l __napi_schedule

Check each function exists in /proc/kallsyms on 6.17.8 before running.
Counters every second: rx_out_of_buffer, rx_buff_alloc_err, rx_congst_umr, the page-pool counters, ch7_poll, ch7_arm, ch7_events, ch7_eq_rearm, ch7_force_irq, all rx7_* error counters, and IRQ 312's line in /proc/interrupts.
Deliverable: two timelines, facts only.
Onset: everything in the second around the last successful poll, including the NAPI kthread's state and CPU, the last interrupt, and whether a wakeup was issued.
Recovery: the first poll after the flood stops, and exactly what triggered it.
Record: an AN-006 addendum with both timelines. Bring them to me before interpreting anything.
If there's no mechanism by the end of Monday: on Tuesday, draft a netdev report covering:
