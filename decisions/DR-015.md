## Instructions for the student: T1b on 4× c6420 (due Fri Oct 2)

**What changed since DR-013.** Placement arms must be defined by their relation to the IRQ core, not just "cross-L3". T1e showed the IRQ core's SMT sibling (cpu 40) stalls 5/8 while another core in the same L3 (cpu 10) was 0/20. The c6420 is also an Intel Xeon: it has no AMD-style core clusters, so its natural boundary is the socket.

**Day 1 (Mon), setup. No flood cells today.**
1. **Write `notes/platform-c6420.md` from commands:**
   - `lscpu`: sockets, NUMA count (check whether sub-NUMA clustering is on), L3 sharing, SMT siblings;
   - the NIC's NUMA node (`/sys/class/net/<if>/device/numa_node`);
   - `ethtool -i` (driver and firmware);
   - `uname -a` and `/proc/cmdline`.
2. **Kernel:** install the same Ubuntu mainline build as the r6615 (`6.17.8-061708-generic`), so only NIC and platform differ.
3. **Steering:** i40e Flow Director (`ethtool -N`) rules sending the flood to one queue, installed idempotently the way preflight v2 does it. Log rule count and adds per cell.
4. **Configuration:** threaded NAPI on; the flooded queue's IRQ affinity forced to one CPU (the "IRQ core"), as on the r6615.
5. **Detector:**
   - **Port the readiness probe:** read the RX descriptor at `next_to_clean` and check its descriptor-done bit. Stranded means the bit is set while `next_to_clean` is frozen for more than 50 ms.
   - **Time-box: 2 days.** If the port isn't working by then, use the coarse detector: the queue's `rx_packets` frozen while port drop counters climb.
   - Record which detector each cell used.
6. **Freeze `specs/p1-T1B.md`** before any cell.

**Arms**, n = 8 each, protocol identical to the r6615 (158k pps, 64 B, one queue, same duration):

| Arm | Poller placement | r6615 analog |
|---|---|---|
| A | SMT sibling of the IRQ core | cpu 40 (5/8) |
| B | Different physical core, same socket | cpu 10 (0/20) |
| C | Other socket | cpu 24 (5/8) |
| D | Unpinned (default) | unpinned (4/8–8/8) |

**Nodes and order.** Two DUT/sender pairs. Each pair runs 4 blocks, each block one cell of every arm in randomized order, so both pairs see every arm equally. This avoids the node and ordering confounds that bit us before (the striding result, the preflight rule growth).

**Decision rule (freeze it):**

| Result | Meaning | Consequence |
|---|---|---|
| Any arm ≥ 3/8, with the probe confirming stranded descriptors | Not mlx5-specific; a host-side threaded-NAPI mechanism is implicated | **T1a's device/firmware call must be revisited before the report goes out.** Stop and tell me |
| All arms ≤ 1/8 | Not reproduced on i40e / Intel Xeon | Report says exactly that. Note the confound: NIC *and* CPU platform both changed |
| Anything else | Inconclusive | Report as inconclusive |

A clean i40e result is expected under either device-side explanation from the last check (firmware stuck, or the arm doorbell not taking effect). i40e re-enables interrupts through a register write, not mlx5's completion-queue arm and event queue, so it doesn't share the suspect mechanism.

**Day 4 (Thu), use the free nodes for the accounting question.** Measure C-014 on a c6420 pair with its stock Ubuntu kernel, using the AN-007 method: hardware counters against `/proc/stat` busy time on the IRQ core under flood. Record `IRQ_TIME_ACCOUNTING`, `NO_HZ_FULL` and `/proc/cmdline`. If that kernel has `IRQ_TIME_ACCOUNTING` unset and no `nohz_full=` on the command line, this directly tests last check's issue 3:
- **An undercount appears:** the criterion is `IRQ_TIME_ACCOUNTING` unset alone, and C-024 widens.
- **None appears:** `nohz_full` is part of the condition, and C-024 is re-derived.

Either way it's a second-platform data point for the paper. It doesn't replace the IRQACCT matched pair on the r6615.

**Only if every arm is clean,** break the confound: 2 nodes of an Intel platform *with* an mlx5 NIC (for example Utah's xl170; verify its NIC on the hardware page first), running arms A, C and D, n = 8. If mlx5 on Intel stalls, it's the mlx5 device on any platform; if not, the AMD platform is part of it.

**Not on the c6420s:** the re-arm test and the watchdog patch are mlx5-specific and stay on the r6615, in parallel.
