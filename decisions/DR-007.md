# DR-007 (final): Find the mechanism

**Date:** September 26, 2026
**Status of the work:** We have a reproducible symptom (a receive queue that stays dead after overload until a channel reset) and one implicated feature (`rx_striding_rq`, the multi-packet RQ). We do **not** yet know the root cause. Until we can state the mechanism in one sentence backed by kernel state, the disclosure stays in draft and the paper has no spine.

**This memo has one goal: the causal chain.** Everything else waits behind it.

## The sentence we need to complete

> Under overload, the multi-packet RQ refill (UMR via the ICOSQ) stops producing completions because **\_\_\_**, so NAPI is never rescheduled and no interrupt re-arms; the queue does not recover when load drops because **\_\_\_**.

Each blank must be filled from **observed kernel state**, not inference. That is Task B, and it is the critical path.

## Priority 1: Task B — read a dead queue's state (start the moment a cell dies)

The dead state is stable, so inspect it at leisure. This is what devlink couldn't give us.

### B0: tooling check (first, 20 minutes)

```
drgn --version
ls /sys/kernel/btf/mlx5_core
# in the build tree: confirm unstripped vmlinux and mlx5_core.ko exist
```

Record which of three paths is available: (a) drgn with BTF, (b) drgn pointed at the unstripped module, (c) a libbpf CO-RE reader on the CQ/ICOSQ pointers already identified in task 2. Use the first that works.

### B1: leave a queue dead

Run one A1 (unpin, 790k) cell, wait for WEDGE, hold 10 s, drop to 158k, and **do not run recovery**. Confirm PROBE-DEAD, then inspect while it stays dead. Keep a healthy queue (any other channel) for comparison.

### B2: dump these fields, dead vs healthy, side by side

For channel 7 and a healthy channel, read and compare:

- **NAPI:** `napi->state`, decoded against the kernel's own enumerators (`prog['NAPI_STATE_SCHED']`, `NAPI_STATE_SCHED_THREADED`, `NAPI_STATE_MISSED`, and the rest). Never hard-code bit numbers.
- **RQ:** producer and consumer indices, and the posted-buffer / stride count.
- **CQ:** consumer and producer indices; is the CQ empty or does it hold unconsumed completions?
- **ICOSQ (the refill queue):** producer and consumer indices; is a UMR work request outstanding and unconsumed?
- Reach these from `netdev_priv(dev, "struct mlx5e_priv")` → channel 7. **Print each struct interactively before assuming any field name.**

### B3: the two questions the dump must answer

1. **Is a completion pending with no event (A), or is there nothing to complete (B)?** The CQ producer/consumer indices decide this: unconsumed entries → A; empty CQ with a stalled ICOSQ → B.
2. **What is the refill path's state?** A UMR outstanding on the ICOSQ with no completion is the specific stall the striding result points to.

### B4: corroborate with counters (add to the PERSIST cells)

Log per second during every PERSIST cell, and especially across a death:

```
ethtool -S enp195s0np0 | grep -E 'rx_congst_umr|rx7_|ch7_|rx_out_of_buffer|rx_buff_alloc_err'
```

A flat ICOSQ and a rising `rx_congst_umr` during a dead queue is strong corroboration that the multi-packet refill path is the stall point.

### B5: what recovery reinitializes

When you do recover the queue, log which ladder step worked and, if drgn is available, dump the same fields immediately before and after the successful step. What the channel reset reinitializes that a `threaded` toggle does **not** tells us what was wedged.

**Deliverable (Task B):** an AN-006 addendum with the dead-vs-healthy field table, the answer to B3 (A or B), and the ICOSQ/UMR counter trace. Facts only, no narrative. **Bring it to me before interpreting.** This is the deliverable the whole program is waiting on.

## Priority 2: Task A with the counterbalanced striding arms

Run this in parallel with Task B; every dead A-cell is also a Task B specimen. Freeze `specs/p1-PERSIST.md` before any run.

**Protocol:** flood to WEDGE or 120 s → hold 10 s → reduce to 158k → monitor 120 s → stop → 20 s wait → 30 s probe at 10k. PROBE-DEAD = probe advance < 270,000. `rxrecover.sh` after every dead cell, logging the reviving step.

**Arms, 10 cells each, one of each per round, 10 rounds:**

| Arm | Wiring | Pre-registered prediction |
|---|---|---|
| A1 | unpin threaded (replication) | PROBE-DEAD ≥ 3/10; falsified at 0/10 |
| **A4** | **default inline, threaded=0, app on core 8** | **Record the count. Any death is the headline.** |
| A5 | default inline, app off-core | Record the count |
| A6 (negative control) | unpin threaded, **flood 525k** (no overload) | 0/10 dead. Any death falsifies overload as the trigger |
| **A7** | unpin, **striding on** | **≥ 8/10 dead (confirmatory)** |
| **A8** | unpin, **striding off** | **≤ 1/10 dead (confirmatory)** |

**A7/A8 order is counterbalanced:** on/off/on/off across the 10 rounds, so arm order is not confounded with the feature. This closes the caveat from the task 4 run. If A8 dies in ≥ 3/10, the multi-packet path is **not** necessary and the mechanism is still open — tell me.

**Same-hour rule:** if any **A4** cell goes PROBE-DEAD, stop and tell me within the hour. The default kernel being exposed changes the disclosure urgency.

**Deliverable (Task A):** `notes/p1-PERSIST-1.md` — per-arm dead counts with 95% intervals, the reviving-step distribution, the firmware header (firmware 20.43.3608, mlx5_core, 6.17.8). Counts only.
